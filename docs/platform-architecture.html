Tournament Platform — Architecture

From "BFL app" to a reusable system for any tournament. Draft v1 · 2026-10-22 · based on the current schema (prisma/schema.prisma, 457 lines) and ARCHITECTURE.md.
Verdict. The current app is a good football-league-with-one-live-season app. It is not yet a tournament platform, and the gap is structural, not cosmetic. Three hard-coded assumptions block everything else — fix those three and every future tournament becomes configuration instead of code.

The three blockers in today's schema

1 · One live season, wiped at rollover

Team, Player, Match have no seasonId. They describe "whatever is active", and the rollover wizard freezes them into resultsJson and deletes them. Two tournaments at once is impossible; history is a JSON blob, not queryable.

2 · Format is an enum

RoundType = LEAGUE | SEMIFINAL | FINAL. Groups, double-elimination, Swiss, brackets of 16, third-place playoffs — none can be expressed. formatConfig Json exists but nothing consumes it generically.

3 · Football is baked in

MatchEventType = GOAL/ASSIST/CARDS, Position = GK/DEF/MID/FWD, standings = 3-1-0, the pitch view = 6-a-side. A basketball, esports or 1v1 tournament cannot reuse any of it.

Design principles

Everything is scoped to an Edition. No "active season" global. Many editions can be live at once; archiving is a status flag, never a delete.
Format and sport are data, not code. Stages, tiebreakers, event types, positions live in config rows that ship with presets. Code only knows the engines (round-robin, knockout, groups…).
Identity ≠ participation. Person and Team persist across editions. Entry and RosterSlot are the per-edition facts. Fixes name changes ("Big Banana → Dilly Dally") and gives real all-time stats via SQL.
Modules are opt-in per edition. Registration, auction, predictions, media, kit reveal, Sheets backup, share graphics — each a toggle. A chess open doesn't need an auction.
Derive, don't store. Standings, stats, brackets are computed from fixtures + events + ruleset (as you already do). Snapshot only when an edition is archived.
Evolve, don't rewrite. Same stack (Next 16 · Prisma · Neon · Netlify). Additive migrations, BFL stays live at every step.

What stays exactly as is

Next.js + Prisma + Neon, derive-on-read standings/stats, polling live updates, audit log, voterId-based anonymous voting, the Kokonut/Motion UI layer, Netlify scheduled functions, round-robin + schedule generators (lib/roundRobin.ts, lib/scheduleRandomizer.ts become the first format engines).

All five fit the architecture. Two need real new modules (player cards, auction stage view); three are configuration of things already in the model. Details below, with the card prototype you can play with.

1 · Players apply themselves

  • Public application page per edition (/{tournament}/{edition}/apply) — no account needed. Organizer chooses which fields appear (core: name, contact, affiliation/semester, position, photo; plus custom questions stored as JSON answers).
  • Edit link: after applying, the player gets a private token link to fix their details/photo until the deadline (same idea as your voterId, but signed).
  • Photo step is guided: upload → in-browser background removal → crop preview as a card. Tips shown ("plain wall, face centred") because photo quality decides card quality.
  • Identity = student ID (from now on). The apply form asks for the student ID (label configurable per tournament). It is stored as a PersonIdentifier(type=STUDENT_ID, value), unique per organization: same ID → same Person, automatically, so all-time stats follow the player across editions and name changes. Visible to organizers only, never on public pages.
  • Past seasons (Season IX and earlier): no IDs exist, so a one-off manual link tool: list of old players on the left, search/create Person on the right, type the student ID once. Unlinked players keep working; they just don't count toward all-time stats until linked.
  • Safety net: if an ID is missing or mistyped, the organizer sees "possible duplicate" suggestions by name and can merge two Persons (audited, reversible).
  • Reviewer queue stays (approve / reject / needs-info). Excel import stays for bulk.

2 · Organizer picks how teams are formed

Edition.formation becomes a strategy (today's two-value TeamFormation enum grows). It's changeable until the edition's rosters are locked.

  • Stage view (/auction/stage, fullscreen, no controls): auto-generated slides from the data — opening slide, then per lot the full player card + base price + live current bid + who's leading, a SOLD stamp with team crest, interstitial team-budget bars, closing squads reveal. Organizer's console advances it; no one builds slides by hand.
  • Three outcomes per lot (suggested): Sold to a team at a price · Unsold (returns for round 2) · Held (parked in a pool, decided at the end). Today you have QUEUED / IN_PROGRESS / SOLD / UNSOLD — add HELD.
  • End-of-auction resolution for held/unsold players: organizer picks per player — assign to a team (free or base price), random fair draw to teams below minimum squad, or leave out of the edition. A "can't close until every team reaches min squad" check prevents illegal rosters.
  • Bidding mode: v1 = organizer-entered (live room, auctioneer types the winner and price — what you built). v2 = team owners bid on their phones with a realtime leader. Recommend shipping v1 first; online bidding adds fairness/latency/dispute problems.
  • Undo any sale (exists), full audit trail, public read-only view for people not in the room.

5 · Manual edit everywhere

  • Every roster fact is editable by organizer at any time: name, photo, position, jersey, team, captain, ratings, tier, even merging two duplicate Persons. Edits write to AuditLog with before/after, so any change can be reverted.
  • Lifecycle-aware rules instead of blocking: before the tournament = free edit; after kickoff = allowed but marked as a transfer/replacement (visible in the log and optionally on the team page); archived = locked, requires an explicit "unlock edition" action.
  • Replacement keeps history: swapping an injured player creates a new RosterSlot linked to the same Person-in-edition rules; goals already scored stay with the original slot, so past stats never get rewritten by an edit.
  • Team managers can edit their own roster (positions, jersey, photo) but not ratings or team membership unless the organizer opens a window.
  • Bulk tools: spreadsheet-style table edit, multi-select move-to-team, undo last bulk change.

              │      └─ Edition (a season/year; status; modules; timezone)
              │            ├─ Stage[] (ordered; format + config + advancement rules)
              │            │     └─ Group[] (optional) → Fixture[] → FixtureSide[] → Event[]

A tournament = ordered Stages. Each stage has a format engine, and an advancement rule that says who moves to the next stage. Pick a preset to see it as data.

Blunt risks


    

  • Over-engineering is the real enemy. A fully generic engine with no second tournament to test against will be wrong. Build engines only for formats a real event needs; keep the rest as enum values that throw "not supported yet".
    • 

  • Single developer. Every module you add is something you maintain. The module-toggle design lets you ship small and add later.
    • 

  • Unexercised flows. Registration, rollover wizard, Excel import and the Season X auction were never click-tested. Building the platform on top of untested flows compounds risk — add a Playwright smoke suite in Phase 0.
    • 

  • Shared prod DB. One bad migration or local test run currently hits the live site. Phase 0 fixes this first for a reason.
